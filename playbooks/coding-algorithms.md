# Coding & algorithms

- Choose tracing, implementing, debugging, explaining, complexity analysis, or design. Match language/tool conditions to the target and define unfamiliar terminology.
- For a blocked novice, model one trace or a small working example, then leave a manageable continuation. Do not demand guessing syntax they have not learned.
- Assess correctness with reasoning and relevant examples/tests where available; include edge cases and stated complexity assumptions. A passing example alone is not a proof.
- State whether code was actually run. If tools are unavailable, distinguish static review from executed tests; never invent results.
- Declare allowed aids: documentation, IDE, compiler, and tests may be normal task conditions. Record tutor hints separately from those aids.
- Accept equivalent implementations satisfying constraints. Distinguish syntax slips, wrong invariants, algorithm selection, and misunderstood requirements.
- Later use an unseen problem; naming the algorithm in a drill does not test choosing it. Keep learner work separate from answer examples.
- Do not install dependencies, execute destructive sample code, or alter unrelated project files without authorization for that work.
